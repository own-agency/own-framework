# OWN Framework — WordPress Theme

Custom WordPress starter theme — a full block theme (`templates/*.html`), built with Tailwind CSS v4, Alpine.js, and Vite (via `vite-plus`). Custom blocks are still built with SCF/ACF (`block.json` + `render.php`), same as ever — full block theme is about page structure and unlocks the native Site Editor Styles experience, not a change to how blocks work.

## Requirements

- WordPress, with the **Secure Custom Fields (SCF)** plugin active — the custom blocks, options pages and field groups (`inc/scf/`, `acf-json/`) depend on it.
- Node.js
- pnpm, pinned via `devEngines.packageManager` in `package.json`

## Getting started

```sh
pnpm install
pnpm dev            # watch mode, development build (theme CSS/JS)
pnpm dev:developer  # watch mode for the developer page (developer/src)
pnpm build          # production build of both
composer install    # Plugin Update Checker (vendor/), for updates
```

## Conventions

- [STRUCTURE.md](STRUCTURE.md) — full layout, the rule that decides where a file
  goes, which names are stored data and must never be renamed, and the comment
  standard.
- [CLAUDE.md](CLAUDE.md) — the same rules condensed for AI coding assistants,
  loaded automatically. Includes the traps that fail silently (Alpine attributes
  vs `wpautop`, dynamic Tailwind classes), why brand identity (colours,
  fonts, shadows) is set entirely through the Site Editor's native Ontwerp
  panel, not a custom options page, and the one deliberate exception to that
  rule — the "Stijlen" options page (Thema opties → Stijlen) that drives
  site-wide border-radius and spacing scales.
- `.claude/skills/new-block` — scaffold or extend a custom block.
- `.claude/skills/safe-refactor` — verified comment cleanup and file renames.

## Project structure

In short — `blocks/` and `parts/` already hold this theme's own custom
blocks and template parts (hero, cta, afbeeldingen-slider, header/footer
blocks, a full vacancy (`vacancy` CPT) block set — archive/single hero,
results grid, apply CTA, a featured-vacancies block for regular pages — and
a full agenda (`agenda` CPT) block set the same way — archive hero + a
filterable/sortable results grid with a list/grid toggle, single-moment
hero, an optional signup CTA, a featured-moments block for regular pages);
`patterns/` and every `template-parts/` subfolder still start empty.
See `STRUCTURE.md` for the full picture.

- `templates/` — block templates (`index.html`, `single.html`, `page.html`, `404.html`, `archive-vacancy.html`, `single-vacancy.html`, `archive-agenda.html`, `single-agenda.html`) — the actual front-end entry point
- `parts/` — Site Editor template parts (Header, Footer — designed via Appearance → Ontwerp)
- `blocks/` — one self-contained folder per custom block (`block.json`, `render.php`, optional `parts/` and `hooks/`)
- `template-parts/` — PHP markup with two or more consumers, called from blocks: `components/`, `shapes/`, `layout/`
- `inc/` — autoloaded PHP: `functions/`, `core-blocks/`, `scf/`
- `patterns/` — WordPress block patterns
- `media/` — static assets served as-is: `icons/`, `vectors/`, `logos/`, `images/`
- `fonts/` — font files (root by convention; `@font-face` paths point here)
- `src/` — build input (Tailwind CSS, JS); `assets/` — build output, gitignored
- `acf-json/` — synced SCF field group definitions
- `index.php` — not used for rendering; exists only because WordPress requires it to recognize a theme at all

## Build tooling

Assets are built with `vite-plus`, a Vite wrapper that also drives Tailwind CSS v4 and this theme's linting. Configuration lives in `vite.config.ts`. Production builds output to `assets/`, which is gitignored and regenerated by `pnpm build`.

## Versioning and updates

The theme version is tracked in two places that must stay in sync (CI checks
this): `Version:` in `style.css` and `version` in `package.json`. Follow
[semantic versioning](https://semver.org/): patch for fixes, minor for new
features, major for breaking changes to templates or block markup.

Sites update the theme like a plugin, via **Netwerkbeheer → Updates**
(Dashboard → Updates on a single site): `inc/functions/updater.php` (Plugin
Update Checker) reads the GitHub releases of this public repository and
installs the attached `own-framework.zip`. That zip is built by
`.github/workflows/release.yml` when a `vX.Y.Z` tag is pushed, and contains
the build output (`assets/`, `developer/build/`, `vendor/`) but not the
sources (`.distignore`). Branches, pull requests and the release steps:
[CONTRIBUTING.md](CONTRIBUTING.md).

Locally, `composer install` adds Plugin Update Checker to `vendor/`; without
it the theme simply doesn't check for updates.
